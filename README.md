# AI 코드 중심 디자인 AX 실행 가이드

## HTML 프로토타입 협업 및 외부 전달

이 저장소의 HTML 산출물 작업과 외부 개발사 전달에는
[기획·디자인 HTML 협업 가이드](./docs/README_HTML_COLLABORATION_GUIDE.md)를 우선 적용한다.
아래의 AX 실행 가이드는 일반적인 탐색·제품화 협업 참고 문서로 유지한다.

- 플랫폼 기본 진입: `index.html`
- 외부 전달 인덱스: `handoff.html`
- 통합 프로토타입 직접 링크: `prototype.html`
- 디자인 시스템 후보안: `system/index.html`
- 화면 원장: `docs/design/screen-registry.json`
- 기준 원본: 추적되는 HTML과 `src/`, `system/`, `assets/`, `docs/`
- `dist/`: 승인된 버전 태그 전달 시 `npm run build`로 생성하는 비추적 산출물

로컬 확인 방법:

```bash
npm start
```

브라우저에서 `http://localhost:4173/`을 열면 플랫폼에 바로 진입한다.
화면과 전달 문서 목록은 `http://localhost:4173/handoff.html`에서 확인한다.
외부 모듈 스크립트와 화면 원장 JSON을 사용하므로 `file://`로 직접 열지 않는다.

### 우리 팀의 실제 전제

- 협업과 구현 보조 도구는 **Codex**를 사용한다.
- 로고·브랜드·히어로 이미지·상징적 일러스트처럼 시각적 판단이 중요한 요소는 **Figma**에서 만든다.
- 일부를 제외하면 개발 지식과 Git 사용 경험이 많지 않다.
- 백엔드와 프론트엔드는 이미 상위기획을 길게 거치지 않고 바이브코딩으로 빠르게 만들고 있다.
- 목표는 짧은 기간 안에 플랫폼을 구축하는 것이지만, 검증되지 않은 방식 때문에 재작업이 늘어날 위험도 함께 관리해야 한다.

이 문서는 기존 기획·디자인·개발 단계를 모두 없애자는 문서가 아니다. **긴 사전 기획을 5–10분짜리 작업 카드로 줄이고, Figma와 Codex의 역할을 나누며, 작은 제품 단위로 빠르게 검증하는 방법**을 정한다.

## 0. 이 문서를 처음 읽는 사람에게

우리 팀은 AI로 화면을 빠르게 만들 수 있다. 하지만 **AI가 만든 화면을 그대로 제품에 넣는 것이 목표는 아니다.**

```text
문제 정의 → 빠른 탐색 → 좋은 안 선택 → 실제 제품 코드에서 발전
→ Preview 리뷰 → 검사 통과 후 병합
```

### 꼭 기억할 6가지

1. Figma는 상징적 비주얼과 시각 방향에 사용하고, Codex는 실제 화면·상태·코드 구현에 사용한다.
2. `design.md`는 안내문이다. 실제 기준은 토큰·컴포넌트·테스트 코드다.
3. Git을 잘 몰라도 작업할 수 있지만, **main에 직접 수정하지 않는다**는 규칙은 모두 지킨다.
4. 공통 컴포넌트는 기능 화면보다 먼저 합의하고 병합한다.
5. 탐색용 프로토타입과 운영 코드로 발전시킬 프로토타입을 시작할 때 구분한다.
6. 최종 전달물은 HTML/CSS 파일이 아니라 **승인된 PR과 Preview URL**이다.

### 이 가이드에서 쓰는 세 단어

| 단어 | 쉬운 뜻 | 팀에서의 약속 |
|---|---|---|
| 작업 브랜치 | 내 작업만 담긴 안전한 복사본 | 모든 Codex 작업은 브랜치에서 시작 |
| Preview | 작업 중인 화면을 브라우저에서 보는 주소 | 코드보다 Preview에서 먼저 리뷰 |
| PR | 내 변경을 제품에 넣어도 되는지 확인받는 요청 | 승인·검사 후에만 병합 |

### 오늘 바로 적용하는 7단계

```text
1. Codex에 저장소를 먼저 읽고 요약하라고 요청한다.
2. Figma 자산과 Codex가 만들 화면을 나눈다.
3. 5–10분 작업 카드로 범위·상태·완료 기준을 적는다.
4. 탐색 레인 또는 제품화 레인을 고른다.
5. 작업 브랜치에서 작은 흐름 하나를 만든다.
6. Preview에서 실제로 눌러 보고 번호를 붙여 수정한다.
7. 검사 통과 후 PR을 올리거나, 막히면 fallback한다.
```

## 1. 작업 시작 전: 레인을 고른다

### Figma와 Codex의 역할을 먼저 나눈다

| 작업 | 기본 도구 | 남겨야 하는 것 |
|---|---|---|
| 로고·브랜드 그래픽·히어로 이미지·상징적 일러스트 | Figma | export 파일, 색상/크기 규칙, 사용 위치 |
| 화면 흐름·레이아웃 아이디어 비교 | Figma 또는 Codex 탐색 레인 | 선택한 흐름과 결정 이유 한 줄 |
| 실제 컴포넌트 조합·반응형·상태 | Codex + 제품 저장소 | 코드, Preview, 상태 목록 |
| 백엔드 API 연결·mock·오류 처리 | Codex + 개발 저장소 | 데이터 가정, 오류/권한 상태 |
| 최종 시각 조정 | Figma에서 만든 자산 + Preview | 변경 요청 번호와 승인 결과 |

Figma에서 만든 핵심 비주얼을 Codex가 임의로 다시 그리게 하지 않는다. 반대로 Figma에서 개발용 화면을 매번 완성하려 하지 않는다. **Figma는 “무엇을 보여줄지”, Codex는 “제품 안에서 어떻게 동작할지”를 담당**한다.

### Figma 자산을 Codex에 넘기는 최소 형식

Figma 링크만 보내지 말고 아래 네 가지를 함께 적는다.

```text
자산 이름: hero-dashboard
파일 형식: SVG / PNG / WebP
사용 위치: 대시보드 첫 화면의 상단 배너
규칙: 비율 유지, 임의 색상 변경 금지, 모바일에서는 숨김
```

파일명에는 역할과 상태를 넣는다. 예: `hero-dashboard-default.svg`, `logo-symbol-dark.svg`, `illustration-empty-search.svg`.

### 개발 지식이 적은 멤버의 기본 작업 방식

모든 멤버가 Git 명령을 외울 필요는 없다. 아래 네 문장만 Codex에 순서대로 요청하면 된다.

```text
1. 이 작업을 위한 안전한 작업 브랜치를 만들어 줘. main은 수정하지 마.
2. 코딩 전에 저장소 구조와 재사용할 컴포넌트를 쉬운 말로 요약해 줘.
3. 구현 후 실행 가능한 Preview를 만들고, 내가 확인할 경로를 알려 줘.
4. 변경 파일, 남은 위험, 검사 결과를 PR 설명용으로 정리해 줘.
```

Git을 직접 다루는 담당자는 최소 1명 지정한다. 그 담당자는 브랜치·PR·병합을 관리하고, 다른 멤버는 Codex와 Preview 중심으로 참여한다. 익숙해진 멤버부터 직접 Git을 사용하면 된다.

### Codex에게 먼저 시킬 일과 나중에 시킬 일

```text
먼저: 저장소 읽기 → 비슷한 코드 찾기 → 계획 요약 → 질문하기
나중에: 파일 수정 → Preview 실행 → 검사 → PR 설명 작성
```

저장소를 읽기 전에 “전체 플랫폼을 만들어 줘”라고 요청하지 않는다. 첫 응답은 코드가 아니라 **현재 구조·재사용 후보·위험·다음 한 단계**여야 한다.

모든 작업은 시작할 때 아래 둘 중 하나를 선택한다.

| 레인 | 언제 사용하나 | 만드는 곳 | 운영 코드 재사용 |
|---|---|---|---:|
| 탐색 레인 | 아이디어·흐름을 비교할 때 | Figma, AI 샌드박스, 별도 HTML 등 | 약속하지 않음 |
| 제품화 레인 | 채택된 안을 기능으로 만들 때 | 제품 저장소의 작업 브랜치 | 리뷰 후 가능 |

### 레인을 바꿔야 하는 신호

- 아직 무엇을 만들지 결정하지 않았는데 운영 저장소부터 크게 고치고 있다 → 탐색 레인으로 이동
- 이미 정해진 기능인데 별도 HTML로 만들고 있다 → 제품화 레인으로 이동
- 코드 재사용이 필요한데 실제 컴포넌트를 쓰지 않고 있다 → 제품화 레인에서 다시 시작

### 탐색 레인의 종료 질문

- 어떤 사용자 문제를 해결하는가?
- 어떤 흐름을 채택했는가?
- 기본·로딩·빈 화면·오류·권한 부족·완료 상태가 무엇인가?
- 수용 기준은 무엇인가?
- 운영 코드로 발전시킬 것인가, 참고 자료로 보관할 것인가?

### 단기 구축을 위한 기본 시간 상자

아래 시간은 성공을 보장하는 약속이 아니라, 작업이 끝없이 늘어나는 것을 막는 **초기 기준**이다.

| 구간 | 목표 시간 | 시간이 끝났을 때 |
|---|---:|---|
| 작업 카드·범위 합의 | 10분 | 모르는 항목을 질문으로 남김 |
| 탐색 레인 | 60–90분 | 방향 1개를 고르거나 폐기 |
| 제품화 수직 슬라이스 | 2–4시간 | Preview에서 한 흐름이 동작 |
| 디자인·개발 리뷰 | 30분 | 수정 목록을 번호로 확정 |
| 재검사·PR 정리 | 30분 | 병합·보류·되돌리기 중 하나 결정 |

시간이 초과되면 더 열심히 코딩하지 말고 아래 중 하나를 선택한다.

- 범위를 줄인다.
- 탐색 레인으로 되돌린다.
- 공통 컴포넌트 문제로 분리한다.
- 개발 담당자에게 막힌 지점을 넘긴다.
- 기존 방식으로 구현하고 이번 파일럿의 기록에 남긴다.

### 30초 의사결정표

```text
상징적 비주얼을 만드는가?       → Figma
아직 흐름을 고르는 중인가?       → 탐색 레인
선택된 흐름을 제품에 넣는가?     → 제품화 레인 + Codex
API가 아직 없는가?               → mock/adapter로 격리
공통 컴포넌트를 바꾸는가?        → 멈추고 별도 PR
같은 오류로 30분 이상 막혔는가?  → 범위 축소 또는 fallback
```

## 2. 표준 작업 순서

### Codex 작업 세션을 여는 첫 문장

새 Codex 작업을 시작할 때 아래 내용을 붙여 넣는다.

```text
이번 작업은 [기능명]이다.
목표는 [사용자가 끝내야 할 행동]이다.
먼저 저장소 구조, 관련 화면, API/타입, 재사용 컴포넌트를 읽고
현재 상태·재사용 후보·위험·다음 한 단계를 쉬운 말로 요약해 줘.
아직 파일을 수정하지 말고, 결정이 필요한 질문을 먼저 해 줘.
main 브랜치는 수정하지 마.
```

요약을 확인한 뒤에만 “구현을 시작해 줘”라고 요청한다. 이 한 단계가 불필요한 재생성과 잘못된 파일 수정을 크게 줄인다.

Codex 대화 하나는 기능 하나만 담당한다. unrelated한 화면을 같은 대화에 계속 붙이지 말고 새 작업을 연다. 작업이 끝나면 Codex에게 다음을 요약시켜 기록한다.

```text
이번 작업의 변경 파일, 아직 임시인 부분, 테스트 결과,
다음 사람이 알아야 할 주의사항을 5줄 이내로 정리해 줘.
```

### Step 1. 작업 카드를 만든다

```md
# 작업명

## 사용자 문제
- 누가, 어떤 상황에서, 무엇을 하기 어려운가:

## 이번 작업의 목표
- 사용자가 완료할 핵심 행동 1개:

## 범위
- 포함:
- 제외:

## 필수 상태
- [ ] 기본  - [ ] 로딩  - [ ] 빈 화면
- [ ] 오류/재시도  - [ ] 권한 부족  - [ ] 완료/성공

## 품질 조건
- 반응형 화면:
- 키보드 사용:
- 접근성:
- 성능/브라우저 제약:

## 완료 기준
- [ ] Preview에서 핵심 흐름이 동작한다.
- [ ] 디자인 시스템 컴포넌트를 사용한다.
- [ ] 자동 검사와 리뷰가 통과한다.
```

### Step 2. 탐색한다

탐색 레인에서는 속도를 우선한다.

- 2–3개의 다른 방향을 비교한다.
- 실제 고객 데이터와 비밀키는 사용하지 않는다.
- 한 안을 너무 오래 다듬지 않는다.
- 선택되지 않은 결과는 “폐기”로 표시하고 보관 여부를 결정한다.
- AI에게 전체 제품을 한 번에 만들라고 하지 않는다. 한 화면·한 흐름씩 요청한다.

#### 탐색용 프롬프트

```text
목표: [사용자 문제와 핵심 행동]
이번 범위: [화면/흐름]
반드시 포함할 상태: 기본, 로딩, 빈 화면, 오류, 완료
이번 단계에서 하지 않을 것: 데이터 연동, 인증, 전역 컴포넌트 변경

먼저 ① 사용자 흐름 2가지 ② 장단점 ③ 필요한 화면과 상태를 제안해 줘.
아직 코드는 작성하지 말고, 선택이 필요한 항목을 질문해 줘.
```

### Step 3. 제품화 여부를 결정한다

탐색 결과가 선택되면 아래 중 하나를 기록한다.

```text
[폐기형] 아이디어 검증과 시연용. 운영 코드 재사용을 약속하지 않음.
[발전형] 실제 제품 저장소에서 구현. PR·테스트·리뷰 대상.
```

결정하지 않은 채 프로토타입을 계속 다듬지 않는다. 발전형으로 바꿀 때는 제품화 레인에서 새 브랜치를 만든다.

### Step 4. 제품화 브랜치를 만든다

브랜치 이름은 사용자 가치 또는 기능으로 쓴다.

```text
design/account-permission-empty-state
design/search-filter-mobile
design/onboarding-error-recovery
```

규칙:

- 한 브랜치 = 한 기능 또는 한 사용자 흐름
- 한 작업자 또는 한 AI 에이전트 = 한 브랜치
- 브랜치마다 Preview URL 생성
- 다른 사람이 같은 브랜치에 직접 커밋하지 않음
- 작업이 커지면 작은 수직 슬라이스로 쪼갬

### Step 5. 기존 시스템을 먼저 찾는다

코드를 쓰기 전에 아래 순서로 검색한다.

```text
1. 비슷한 화면 검색
2. 사용할 토큰 검색
3. 같은 역할의 컴포넌트 검색
4. Storybook 사용 예 확인
5. 그래도 없을 때만 신규 컴포넌트 제안
```

```text
새 컴포넌트를 만들기 전에 저장소에서 Card, Panel, Surface, EmptyState를 찾아 줘.
각 컴포넌트의 차이와 이번 요구사항에 가장 적합한 것을 표로 정리해.
기존 것으로 해결할 수 있으면 새 컴포넌트를 만들지 마.
```

### Step 5.5. 백엔드와 프론트엔드의 약속을 확인한다

백엔드와 프론트엔드를 동시에 Codex로 만들 때는 화면부터 고정하지 않는다. 먼저 아래 네 가지를 확인한다.

```text
1. 어떤 데이터가 들어오는가?
2. 아직 API가 없으면 어떤 mock 데이터를 사용할 것인가?
3. 로딩·빈 결과·오류·권한 부족일 때 무엇을 보여줄 것인가?
4. API가 바뀌면 어느 화면과 테스트가 영향을 받는가?
```

프론트엔드와 백엔드가 아직 맞지 않으면 `임시 가정`으로 표시한다. 가정을 실제 사실처럼 숨기지 않는다.

Codex 요청 예시:

```text
이 화면을 구현하기 전에 관련 API, 타입, mock 데이터를 찾아 줘.
현재 확정된 것과 임시 가정을 표로 나누고,
API가 준비되지 않은 부분은 adapter로 격리해 줘.
화면 코드에 임시 데이터가 직접 섞이지 않게 해.
```

### Step 6. 실제 컴포넌트로 발전시킨다

- 색상·간격·폰트는 토큰을 사용한다.
- 공용 컴포넌트의 허용된 variant를 사용한다.
- 데이터가 없으면 데이터 계층만 mock한다.
- 라우팅·상태·키보드·포커스는 실제 제품 방식으로 연결한다.
- 새 prop이나 variant가 필요하면 구현 전에 PR 설명에 이유를 적는다.
- 화면 하나가 아니라 사용자 흐름이 끝까지 동작하도록 만든다.

#### 제품화용 프롬프트

```text
이 작업은 실제 제품 저장소의 발전형 프로토타입이다.

규칙:
- design.md와 기존 토큰/컴포넌트를 먼저 읽는다.
- 임의 hex, 임의 spacing, 새 CSS 시스템을 만들지 않는다.
- 기존 컴포넌트로 해결 가능한지 먼저 검색한다.
- 새 컴포넌트가 필요하면 구현 전에 이유와 API를 제안한다.
- 기본/로딩/빈 화면/오류/권한 부족/완료 상태를 모두 반영한다.
- 질문이 필요한 경우 추측하지 말고 멈춰서 질문한다.

이번 변경:
- 사용자 흐름:
- 변경 화면:
- 수용 기준:
- 사용해야 할 기존 컴포넌트:
```

### Step 7. Preview에서 리뷰한다

코드만 보고 디자인 승인하지 않는다. Preview에서 다음 순서로 확인한다.

1. 핵심 흐름을 처음부터 끝까지 실행한다.
2. 기본·로딩·빈 화면·오류·권한 부족·완료 상태를 각각 연다.
3. 모바일과 데스크톱에서 확인한다.
4. 키보드만으로 주요 행동을 수행한다.
5. 이상이 있으면 스크린샷에 화살표와 번호를 표시해 수정 요청한다.

수정 요청은 전체 재생성보다 변경 단위로 한다.

```text
[수정 1] 모바일에서 필터 버튼이 제목과 겹침. 첨부 이미지의 ① 위치를 확인.
[수정 2] 오류 상태에 재시도 버튼과 원인 설명 추가.
[수정 3] 기존 color.text.secondary 토큰 사용.
위 세 항목만 수정하고 나머지 레이아웃은 유지해.
```

### Step 8. 검사 후 PR을 올린다

```text
- 타입/빌드
- 린트
- interaction
- 접근성
- 시각 회귀
- 반응형 Preview
```

PR에는 반드시 다음을 포함한다.

- 무엇을 바꾸었는가
- Preview URL
- 상태별 확인 결과
- 공통 컴포넌트·토큰 변경 여부

## 3. 공통 컴포넌트 변경 규칙

공통 컴포넌트는 일반 기능 화면과 다르게 다룬다.

```text
기능 브랜치에서 공통 컴포넌트 수정
  → 즉시 멈춤
  → 공통 변경만 담은 별도 PR 작성
  → 디자인 시스템 담당자 승인
  → 공통 PR 병합
  → 기능 브랜치 최신화
  → 기능 작업 계속
```

### 신규 컴포넌트 승인 질문

- 기존 컴포넌트 조합으로 해결할 수 없는가?
- 이름과 책임이 한 문장으로 설명되는가?
- 상태와 variant가 정의됐는가?
- 사용처가 두 곳 이상인가, 한 화면의 예외인가?
- 접근성·모바일 동작이 정의됐는가?
- Storybook 예제가 있는가?

한 화면에서만 필요한 예외라면 공용 컴포넌트로 승격하지 말고 페이지 내부 조합으로 해결한다.

### 공통 파일 소유권 예시

```text
/src/tokens/**       디자인 시스템 담당자 + 프론트엔드 담당자
/src/components/**   디자인 시스템 담당자 + 프론트엔드 담당자
/src/pages/**        해당 기능 담당자
/src/routes/**       프론트엔드 담당자
```

## 4. `design.md` 팀용 최소 템플릿

```md
# Design Rules

## Source of truth
- Tokens: [경로]
- Components: [경로]
- Stories: [경로]
- Accessibility rules: [경로]

## Before coding
1. 비슷한 화면과 컴포넌트를 검색한다.
2. 사용할 토큰과 상태를 적는다.
3. 새 컴포넌트가 필요하면 먼저 제안한다.

## Non-negotiable
- 임의 hex 금지
- 임의 spacing 금지
- 기존 컴포넌트 우선
- 상태 누락 금지
- 접근성 검사 없는 병합 금지
- 공통 파일 변경은 별도 PR

## Required states
- default
- loading
- empty
- error/retry
- permission denied
- success

## Stop and ask
- 기존 컴포넌트 중 선택이 어려울 때
- 토큰에 없는 시각 값이 필요할 때
- 공통 컴포넌트 API를 바꿔야 할 때
- 요구사항과 기존 규칙이 충돌할 때
```

문서와 실제 코드가 다르면 문서를 믿고 진행하지 말고, 원천 코드와 문서를 함께 수정한다.

## 5. 팀 협업 약속

### 일일 협업

- 작업 시작 시 담당 브랜치와 Preview를 공유한다.
- 공통 경로를 건드릴 예정이면 먼저 알린다.
- AI가 새 컴포넌트를 제안하면 구현 전에 팀 채널에 공유한다.
- 리뷰 요청에는 “무엇을 봐야 하는지”를 세 문장 이내로 적는다.

### 리뷰 순서

```text
1. 사용자 흐름이 맞는가?
2. 상태가 빠짐없이 있는가?
3. 기존 디자인 시스템을 사용했는가?
4. 모바일·키보드·접근성이 괜찮은가?
5. 코드 구조와 테스트가 운영 가능한가?
```

### 리뷰 요청 예시

```text
모바일 375px에서 제목과 CTA가 겹칩니다. Preview의 /search 화면에서 재현됩니다.
전체 레이아웃을 다시 만들기보다 기존 Stack 간격 토큰으로 수정해 주세요.
```

## 6. 상태·접근성·반응형 체크리스트

### 상태

- [ ] 정상 데이터
- [ ] 데이터 0건
- [ ] 느린 네트워크/로딩

- [ ] 입력 오류
- [ ] 저장 성공
- [ ] 취소·뒤로가기

- [ ] 키보드로 핵심 흐름 수행
- [ ] 포커스가 보임

- [ ] 버튼·입력 요소 이름이 분명함

- [ ] 텍스트 대비 확인

### 반응형

- [ ] 작은 모바일

- [ ] 데스크톱
- [ ] 긴 문구·긴 이름·긴 숫자
- [ ] 확대 보기
- [ ] 불필요한 가로 스크롤 없음

## 7. AI를 효율적으로 사용하는 법

### AI에게 맡기기 좋은 일

- 여러 레이아웃 방향 비교
- 반복적인 컴포넌트 조합
- 상태별 화면 초안
- 기존 코드에서 비슷한 구현 찾기
- 테스트 케이스 초안
- Preview의 명확한 수정사항 반영

### 사람이 결정할 일

- 어떤 사용자 문제를 우선할지
- 어떤 흐름을 제품에 채택할지
- 공통 컴포넌트의 이름과 책임
- 예외를 시스템에 넣을지 페이지에 둘지
- 접근성·보안·데이터 처리의 최종 승인
- 제품에 남길 것과 버릴 것

### AI가 멈추고 질문해야 하는 상황

- 기존 컴포넌트 중 무엇을 쓸지 모를 때
- 토큰에 없는 색상·간격이 필요할 때
- 공통 컴포넌트 API를 변경해야 할 때
- 오류·권한·저장 상태가 정의되지 않았을 때
- 요구사항과 코드 규칙이 충돌할 때

프롬프트 운영 규칙은 간단하다: 처음부터 전체 재생성하지 말고, 수정 번호를 붙이고, 스크린샷에 위치를 표시하고, “나머지는 유지”할 범위를 적고, 변경 후 검사를 다시 실행한다.

## 8. 자주 생기는 문제와 즉시 대응

| 문제 | 즉시 할 일 | 다시 생기지 않게 할 일 |
|---|---|---|
| 화면마다 간격이 다름 | 임의 값을 토큰으로 교체 | raw spacing lint 추가 |
| 비슷한 컴포넌트가 두 개 생김 | 사용처와 책임 비교 후 하나 선택 | 신규 컴포넌트 검색 의무화 |
| 문서와 코드 규칙이 다름 | 원천 코드 기준으로 정정 | 문서 동기화 PR 포함 |
| 두 브랜치가 공통 파일 수정 | 공통 변경을 별도 PR로 분리 | `CODEOWNERS` 적용 |
| Preview는 예쁜데 운영 연결이 어려움 | 발전형이면 제품 저장소에서 재구현 | 레인 선택을 시작 시 기록 |
| AI가 오류·빈 상태를 빠뜨림 | 상태 체크리스트로 보완 | 작업 카드에 필수 상태 고정 |
| 수정할 때마다 다른 곳이 깨짐 | 전체 재생성 중단, delta 수정 | 번호 붙인 수정과 회귀 검사 |
| 리뷰가 주관적임 | 수용 기준과 Preview로 대화 | PR 템플릿에 판단 기준 포함 |

### 시간이 더 들기 시작했을 때의 중단 기준

AX 도입의 가장 큰 위험은 “조금만 더 고치면 된다”는 상태가 길어지는 것이다. 다음 중 하나면 실험을 멈추고 담당자에게 넘긴다.

- 같은 화면을 AI가 두 번 이상 전체 재생성했는데 문제가 남아 있다.
- 30분 이상 같은 오류를 해결하지 못하고 있다.
- 화면을 고치기 위해 공통 컴포넌트 API를 계속 바꾸고 있다.
- Preview는 좋아졌지만 실제 API·권한·오류 처리가 연결되지 않는다.
- 리뷰어가 무엇을 승인해야 하는지 합의되지 않았다.

중단했다고 실패한 것이 아니다. 범위를 줄이거나 기존 개발 방식으로 전환하고, 왜 전환했는지만 작업 카드에 남긴다. 파일럿의 목적은 모든 작업을 Codex로 처리하는 것이 아니라 **전체 리드타임을 줄이는 것**이다.

### fallback 규칙

아래 조건이면 해당 작업은 전통적 구현 방식으로 마무리할 수 있다.

```text
1. 사용자 흐름과 수용 기준은 유지한다.
2. 탐색 결과와 Figma 핵심 비주얼은 개발팀에 전달한다.
3. Codex가 만든 코드는 참고 자료로만 남긴다.
4. 재작업에 들어간 시간과 원인을 파일럿 지표에 기록한다.
```

## 10. 처음 6주 운영안

### 1–2주차: 기반 준비

- 대표 프론트엔드 스택 하나 선정
- Git을 직접 다루는 AX/프론트 담당자 1명 지정
- 나머지 멤버가 Codex와 Preview로 참여하는 방법 30분 온보딩
- 색상·타이포·간격·radius 토큰 정의
- 핵심 컴포넌트 10–15개 정의
- Storybook 또는 동등한 사용 예제 구축
- `design.md`, `CODEOWNERS`, PR 템플릿 작성
- Preview와 기본 검사 연결
- Figma 핵심 비주얼의 파일명·export 규칙 정의

### 3–5주차: 기능 하나 실행

내부 도구 또는 위험이 낮은 기존 기능을 고른다.

- 화면 2–4개
- 핵심 사용자 흐름 1개
- 로딩·빈 화면·오류 포함
- 공통 컴포넌트 사용
- Figma 상징 요소 1–2개를 실제 화면에 연결
- 프론트·백엔드 mock/API 가정을 문서화
- 실결제·대규모 인증·전사 정보구조 개편은 제외

탐색 시간, 제품화 시간, 개발 재가공 시간을 나눠 기록한다.

### 6주차: 계속할지 결정

- 아이디어에서 승인 PR까지 빨라졌는가?
- 개발자가 화면을 다시 만드는 시간이 줄었는가?
- 임의 값·중복 컴포넌트가 늘지 않았는가?
- 접근성·시각 회귀·배포 후 UI 결함이 악화되지 않았는가?

속도만 빨라지고 품질이 나빠졌다면 성공으로 보지 않는다.

## 11. 하지 말아야 할 것

- `design.md`만 만들고 디자인 시스템 없이 전면 도입
- AI가 만든 HTML/CSS를 무검토로 운영 반영
- 여러 사람이 같은 브랜치에서 직접 수정
- 기능 PR에 공통 컴포넌트 변경을 몰래 포함
- 화면이 예쁘다는 이유로 상태·접근성 검사를 생략
- Figma 사용량 감소를 성과로 삼기
- 여러 프론트엔드 스택의 디자인 시스템을 동시에 만들기
- 전체 코드를 매번 재생성해 수정사항을 반영하기
- 신규 컴포넌트를 한 화면의 예외인데 바로 공용화

## 12. 한 장 요약: 작업자용 카드

```text
시작 전
□ 탐색 레인인가, 제품화 레인인가?
□ 사용자 문제와 완료 기준이 적혀 있는가?
□ Figma에서 만들 요소와 Codex에서 만들 요소를 나눴는가?

코딩 전
□ 비슷한 화면·토큰·컴포넌트를 검색했는가?
□ 새 컴포넌트가 필요하면 먼저 제안했는가?
□ 필수 상태를 정했는가?
□ API/타입/mock 가정을 확인했는가?

작업 중
□ 내 브랜치와 Preview에서 작업하는가?
□ 임의 색상·간격·폰트를 만들지 않았는가?
□ 수정은 작은 delta로 요청했는가?

PR 전
□ 기본·로딩·빈 화면·오류·권한·완료를 확인했는가?
□ 모바일·키보드·접근성을 확인했는가?
□ 자동 검사를 통과했는가?
□ Preview URL과 확인 방법을 적었는가?

멈춰야 할 때
□ 공통 컴포넌트 API를 바꿔야 하는가?
□ 토큰에 없는 값이 필요한가?
□ 요구사항과 기존 규칙이 충돌하는가?
→ 추측하지 말고 담당자에게 질문한다.
```

## 13. 이미 해 본 조직에서 가져올 것

성공 사례를 그대로 복사할 수는 없지만, 공통적으로 반복된 운영 방법은 가져올 수 있다.

| 사례 | 우리 팀이 가져올 한 가지 |
|---|---|
| Knak | 디자이너에게 Codex를 주기 전에 저장소와 컴포넌트를 안전하게 정리한다. |
| Vercel Design Engineering | 정적 handoff 대신 디자이너와 개발자가 Preview에서 함께 확인한다. |
| Basecamp Shape Up | 전체 플랫폼을 한 번에 만들지 않고 작은 수직 슬라이스를 끝낸다. |
| monday.com | Figma 링크만 주지 말고 실제 토큰·컴포넌트·코드 규칙을 Codex에 제공한다. |
| Atlassian | `design.md`를 설명문으로만 두지 말고 코드 원천·검사·사용 예와 연결한다. |
| 40명 조직의 코드 중심 전환 사례 | Figma를 즉시 없애지 않고, 내부 도구와 작은 개선부터 연습한다. |

이 사례들은 “Codex를 쓰면 반드시 몇 배 빨라진다”는 약속이 아니다. 성공 조건을 먼저 만들고 작은 범위에서 확인했다는 점이 핵심이다.

### 우리 팀의 성공 판정

다음 세 항목이 모두 좋아질 때만 확장한다.

1. 작업 카드부터 Preview 승인까지의 시간이 짧아졌다.
2. 개발팀이 화면을 다시 만드는 시간이 줄었다.
3. UI 결함·접근성 누락·공통 컴포넌트 중복이 늘지 않았다.

속도만 빨라지고 품질이 나빠지면 Codex 사용 범위를 줄이고, Figma 탐색 + 전통적 구현의 혼합 방식으로 돌아간다.
