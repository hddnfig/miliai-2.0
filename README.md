# miliai-2.0

# GitHub & AI 협업 가이드

이 프로젝트는 여러 작업자가 GitHub를 통해 협업하며, Cursor, Claude Code, Codex 등 다양한 AI 개발 도구를 활용하여 코드를 작성합니다.

AI 도구별로 서로 다른 방식의 코드가 생성되거나, 다른 작업자의 작업 범위를 침범하는 문제를 방지하기 위해 모든 작업자는 아래 규칙을 공통으로 준수해야 합니다.

---

## 1. 기본 원칙

모든 작업은 다음 원칙을 기준으로 진행합니다.

* `main` 또는 `develop` 브랜치에서 직접 작업하지 않습니다.
* 작업별로 새로운 브랜치를 생성합니다.
* 요청받은 범위 안에서만 코드를 수정합니다.
* 기존 프로젝트 구조와 코딩 컨벤션을 우선합니다.
* 기존 공통 컴포넌트와 유틸리티를 최대한 재사용합니다.
* AI가 생성한 코드는 작업자가 직접 검토한 후 반영합니다.
* 별도의 요청 없이 AI가 임의로 commit, push, merge, deploy를 수행하지 않도록 합니다.
* 다른 작업자의 브랜치나 코드를 임의로 수정하지 않습니다.
* 작업 완료 후 Pull Request를 통해 코드 리뷰를 진행합니다.

---

## 2. 전체 작업 흐름

모든 작업은 다음 순서로 진행합니다.

```text
Issue 또는 작업 정의
→ 기준 브랜치 최신화
→ 작업 브랜치 생성
→ 코드 작업
→ 로컬 검증
→ Commit
→ Push
→ Pull Request 생성
→ 코드 리뷰
→ Merge
```

---

## 3. 작업 시작 전 확인

작업을 시작하기 전에 다음 항목을 확인합니다.

1. 현재 브랜치
2. 기준 브랜치의 최신 상태
3. 작업 중인 다른 브랜치
4. 관련 Issue 또는 작업 요청
5. 관련 Figma 및 기획 문서
6. 프로젝트 폴더 구조
7. 기존 유사 기능 또는 컴포넌트
8. 현재 프로젝트의 코딩 컨벤션
9. 변경 예정 파일과 영향 범위

관련 기능이 이미 구현되어 있다면 새로운 방식을 만들기보다 기존 구현 방식을 우선적으로 사용합니다.

---

## 4. 기준 브랜치

프로젝트에 `develop` 브랜치가 있는 경우 `develop`을 기준으로 작업합니다.

`develop` 브랜치가 없는 경우 `main`을 기준으로 작업합니다.

```bash
git checkout develop
git pull origin develop
```

또는

```bash
git checkout main
git pull origin main
```

기준 브랜치에서 직접 코드를 수정하거나 commit하지 않습니다.

---

## 5. 브랜치 생성 규칙

모든 작업은 별도의 브랜치에서 진행합니다.

### 브랜치 이름 형식

```text
작업유형/작업내용
```

### 작업 유형

| 작업 유형   | Prefix      | 예시                      |
| ------- | ----------- | ----------------------- |
| 신규 기능   | `feature/`  | `feature/user-login`    |
| 버그 수정   | `fix/`      | `fix/mobile-header`     |
| UI 수정   | `ui/`       | `ui/home-card-hover`    |
| 리팩터링    | `refactor/` | `refactor/api-client`   |
| 문서 수정   | `docs/`     | `docs/update-readme`    |
| 테스트     | `test/`     | `test/login-validation` |
| 설정 및 기타 | `chore/`    | `chore/update-eslint`   |
| 긴급 수정   | `hotfix/`   | `hotfix/payment-error`  |

브랜치명은 영문 소문자와 하이픈을 사용합니다.

```bash
git checkout -b ui/home-card-hover
```

GitHub Issue가 있는 경우 Issue 번호를 포함할 수 있습니다.

```text
feature/123-user-login
fix/245-mobile-header
```

브랜치 이름만 보고도 어떤 작업인지 알 수 있도록 명확하게 작성합니다.

---

## 6. 작업 범위 규칙

AI와 함께 작업할 때는 요청된 범위 안에서만 코드를 수정합니다.

### 별도 협의 없이 수정하지 않는 항목

* 관련 없는 파일
* 다른 작업자가 담당하는 화면
* 공통 컴포넌트 구조
* 전역 스타일
* 디자인 토큰
* 라우팅 구조
* 공통 API 모듈
* 데이터베이스 스키마
* 환경 변수
* 패키지 버전
* CI/CD 설정
* 프로젝트 전체 폴더 구조
* 기존 기능의 이름
* 프로젝트 전체 코드 포맷

요청 범위를 넘어서는 변경이 필요하면 먼저 다음 내용을 공유합니다.

```text
- 추가 변경이 필요한 이유
- 변경 대상 파일
- 예상 영향 범위
- 변경하지 않았을 경우 발생하는 문제
- 가능한 대안
```

승인되지 않은 범위는 임의로 수정하지 않습니다.

---

## 7. 기존 코드 우선 원칙

새로운 코드를 작성하기 전에 프로젝트 내 유사 구현을 확인합니다.

다음 항목이 이미 존재한다면 우선적으로 재사용합니다.

* 공통 UI 컴포넌트
* 디자인 시스템 컴포넌트
* 컬러 및 타이포그래피 토큰
* 유틸리티 함수
* Custom Hook
* API 호출 모듈
* 타입 정의
* 상태 관리 방식
* 폼 검증 방식
* 로딩 UI
* 에러 UI
* 빈 상태 UI
* 반응형 처리 방식

동일한 역할을 하는 컴포넌트나 함수를 중복으로 생성하지 않습니다.

기존 코드와 다른 새로운 패턴이 필요한 경우, 도입 이유를 작업자와 먼저 논의합니다.

---

## 8. AI 활용 규칙

AI는 코드 작성을 지원하는 도구이며, 최종 판단과 책임은 작업자에게 있습니다.

### AI가 작업 전에 확인해야 하는 내용

AI에게 다음 내용을 먼저 확인하도록 요청합니다.

* 현재 브랜치
* Git 변경 상태
* 기준 브랜치
* 관련 파일
* 프로젝트 구조
* 기존 코드 스타일
* 유사 컴포넌트
* 작업 영향 범위

### AI에게 바로 코드를 수정시키지 않기

작업 범위가 크거나 공통 영역을 수정하는 경우, AI에게 먼저 다음 내용을 요청합니다.

```text
1. 작업 내용을 이해한 결과
2. 구현 계획
3. 변경 예정 파일
4. 기존 코드에 미치는 영향
5. 충돌 가능성이 있는 영역
```

계획을 검토한 후 코드 수정을 진행합니다.

### AI가 임의로 하면 안 되는 작업

AI가 별도의 요청 없이 다음 작업을 수행하지 않도록 합니다.

* commit
* push
* merge
* rebase
* force push
* 브랜치 삭제
* 패키지 설치
* 패키지 삭제
* 라이브러리 버전 변경
* 환경 변수 수정
* 데이터베이스 마이그레이션
* 배포
* 대량 파일 삭제
* 프로젝트 전체 리팩터링
* 전체 코드 포맷팅
* 기존 기능 삭제

## 9. 공통 AI 작업 프롬프트

각 작업자는 사용하는 AI에게 아래 프롬프트를 전달한 후 작업을 진행합니다.

```text
당신은 여러 명의 작업자가 GitHub를 통해 협업하는 프로젝트의 AI 개발자입니다.

이 프로젝트에서는 여러 작업자가 서로 다른 AI 도구를 사용하므로, 기존 코드를 임의로 변경하거나 다른 작업자의 작업 범위를 침범해서는 안 됩니다.

README에 작성된 GitHub & AI 협업 가이드를 모든 작업보다 우선하여 준수하세요.

작업을 시작하기 전에 반드시 다음 내용을 확인하세요.

1. 현재 브랜치
2. Git 변경 상태
3. 기준 브랜치의 최신 상태
4. 프로젝트 폴더 구조
5. 기존 코딩 컨벤션
6. 관련 컴포넌트 및 유사 구현
7. 작업 범위와 영향받는 파일

main, master, develop 브랜치에서 직접 작업하거나 commit하지 마세요.

작업 브랜치가 없다면 다음 규칙에 맞는 브랜치명을 제안하세요.

- 신규 기능: feature/작업명
- 버그 수정: fix/작업명
- UI 수정: ui/작업명
- 리팩터링: refactor/작업명
- 문서 수정: docs/작업명
- 설정 변경: chore/작업명

요청받은 작업 범위 안에서만 코드를 수정하세요.

다음 행동은 별도 승인 없이 진행하지 마세요.

- 관련 없는 파일 수정
- 전체 코드 포맷팅
- 폴더 구조 변경
- 공통 컴포넌트 구조 변경
- 패키지 추가 또는 삭제
- 라이브러리 버전 변경
- API 인터페이스 변경
- 데이터베이스 스키마 변경
- 환경 변수 변경
- 전역 스타일 변경
- 기존 기능 삭제
- 다른 코드 리팩터링
- commit
- push
- merge
- deploy

새로운 코드를 작성하기 전에 기존 프로젝트에 동일하거나 유사한 구현이 있는지 확인하세요.

기존에 다음 요소가 있다면 우선 재사용하세요.

- 공통 컴포넌트
- 디자인 토큰
- 유틸리티 함수
- 타입
- Custom Hook
- API 모듈
- 상태 관리 로직
- 로딩, 에러, 빈 상태 패턴

바로 코드를 수정하지 말고 먼저 다음 내용을 보고하세요.

1. 작업 이해 내용
2. 구현 계획
3. 변경 예정 파일
4. 기존 코드에 미치는 영향
5. 예상되는 충돌 가능성
6. 추가 확인이 필요한 내용

작업 범위를 넘어서는 변경이 필요하면 임의로 수정하지 말고 이유와 대안을 먼저 설명하세요.

작업 완료 후에는 다음 형식으로 결과를 정리하세요.

- 작업 요약
- 변경 파일
- 주요 구현 내용
- 실행한 검증
- 확인이 필요한 항목
- 충돌 가능성 및 주의사항

검증하지 않은 항목을 검증했다고 표현하지 마세요.
```

## 11. 디자인 구현 규칙

Figma 또는 디자인 가이드가 제공된 경우 다음 우선순위를 따릅니다.

```text
프로젝트 디자인 시스템
→ 공통 컴포넌트
→ 디자인 토큰
→ Figma 명세
→ 기존 화면 패턴
```

AI가 Figma 화면을 임의로 해석하여 새로운 디자인 스타일을 만들지 않도록 합니다.

### UI 구현 시 확인 항목

* Default
* Hover
* Focus
* Active
* Selected
* Disabled
* Loading
* Error
* Empty
* 모바일 반응형
* 태블릿 반응형
* 데스크톱 반응형
* 긴 텍스트
* 데이터가 없는 경우
* 이미지가 없는 경우
* 키보드 접근성
* 스크린 리더 접근성

Figma에 표시되지 않은 예외 상황은 기존 프로젝트의 UI 패턴을 따릅니다.

## 12. 패키지 설치 규칙

새로운 라이브러리나 패키지를 임의로 설치하지 않습니다.

패키지 설치가 필요하다면 먼저 다음 내용을 공유합니다.

```text
- 패키지명
- 사용 목적
- 기존 코드만으로 구현하기 어려운 이유
- 프로젝트 및 번들에 미치는 영향
- 유지보수 상태
- 대체 가능한 방법
```

작업자 또는 담당자의 확인 후 설치합니다.

패키지를 설치한 경우 다음 파일 변경 여부를 반드시 확인합니다.

* `package.json`
* `package-lock.json`
* `yarn.lock`
* `pnpm-lock.yaml`

사용 중인 패키지 매니저에 해당하는 lock 파일만 변경되어야 합니다.

## 13. Commit 규칙

하나의 Commit에는 하나의 명확한 변경 목적만 포함합니다.

### Commit 메시지 형식

```text
type: 변경 내용
```

### Commit Type

| Type       | 설명             |
| ---------- | -------------- |
| `feat`     | 신규 기능          |
| `fix`      | 버그 수정          |
| `ui`       | UI 및 스타일 수정    |
| `refactor` | 기능 변경 없는 구조 개선 |
| `docs`     | 문서 수정          |
| `test`     | 테스트 코드         |
| `chore`    | 설정 및 기타 작업     |

### 예시

```text
feat: add user profile editing
fix: prevent duplicate form submission
ui: apply hover motion to content cards
refactor: simplify API response handling
docs: add AI collaboration guide
chore: update lint configuration
```

다음과 같이 의미를 알기 어려운 메시지는 사용하지 않습니다.

```text
update
수정
작업 완료
final
fix
test
```

## 14. 작업 완료 전 검증

작업 완료 후 가능한 범위에서 다음 항목을 확인합니다.

### 코드 검증

* Type Check
* Lint
* Unit Test
* Integration Test
* Build

프로젝트에 정의된 명령어를 사용합니다.

예시:

```bash
npm run type-check
npm run lint
npm run test
npm run build
```

또는

```bash
pnpm type-check
pnpm lint
pnpm test
pnpm build
```

실행할 수 없거나 프로젝트에 정의되지 않은 명령어는 억지로 실행하지 않습니다.

### 화면 검증

* 요청한 기능이 정상적으로 동작하는지
* 기존 기능에 영향을 주지 않는지
* 모바일에서 정상적으로 보이는지
* 데스크톱에서 정상적으로 보이는지
* 콘솔 에러가 발생하지 않는지
* 로딩 상태가 정상적으로 제공되는지
* 에러 상황이 처리되는지
* 빈 상태가 처리되는지
* 긴 텍스트가 레이아웃을 깨뜨리지 않는지

### Git 검증

```bash
git status
git diff
```

다음 내용을 확인합니다.

* 관련 없는 파일이 변경되지 않았는지
* 디버깅 코드가 남아 있지 않은지
* 불필요한 로그가 남아 있지 않은지
* 민감한 정보가 포함되지 않았는지
* 환경 변수 파일이 포함되지 않았는지
* 자동 생성 파일이 불필요하게 변경되지 않았는지

## 15. Push 규칙

작업 검증 후 자신의 작업 브랜치로 Push합니다.

```bash
git push origin 브랜치명
```

예시:

```bash
git push origin ui/home-card-hover
```

다음 명령어는 사용하지 않습니다.

```bash
git push --force
```

불가피하게 강제 Push가 필요한 경우 반드시 팀원과 먼저 협의합니다.

## 17. AI 코드 검수 프롬프트

Pull Request를 생성하기 전에 AI에게 아래 프롬프트로 변경사항 검수를 요청할 수 있습니다.

```text
현재 작업 브랜치의 변경사항을 기준 브랜치와 비교하여 검수해 주세요.

코드를 바로 수정하지 말고 먼저 문제점을 분석하여 보고하세요.

다음 항목을 확인하세요.

## 작업 범위

- 요청받은 범위를 벗어난 수정이 있는지
- 관련 없는 파일이 변경되었는지
- 불필요한 리팩터링이 포함되었는지
- 공통 기능을 중복으로 구현했는지

## Git 변경사항

- 기준 브랜치에서 정상적으로 분기했는지
- 불필요한 파일이 변경되었는지
- lock 파일이나 설정 파일이 불필요하게 변경되었는지
- 충돌 가능성이 높은 공통 파일을 과도하게 수정했는지

## 코드 품질

- 타입 오류 가능성
- 런타임 오류 가능성
- 중복 코드
- 하드코딩
- 사용하지 않는 코드
- 사용하지 않는 import
- 예외 처리 누락
- 불필요한 상태
- 불필요한 렌더링
- 기존 코드 컨벤션 위반

## UI 및 UX

- 디자인 시스템과 다른 스타일 사용 여부
- 공통 컴포넌트 재사용 여부
- hover, focus, active, disabled 상태
- 로딩, 에러, 빈 상태
- 모바일 및 데스크톱 반응형
- 긴 텍스트 예외 상황
- 키보드 및 스크린 리더 접근성

## 보안

- API Key 및 민감 정보 노출
- 사용자 입력 검증 누락
- 권한 검증 누락
- 로그에 개인정보 포함 여부
- 보안상 위험한 코드

## 검증

가능하다면 프로젝트에 정의된 다음 검증을 실행하세요.

- Type Check
- Lint
- Test
- Build

실행하지 못한 검증은 실행하지 못했다고 명시하세요.

결과는 다음 형식으로 정리하세요.

### 반드시 수정해야 하는 문제

PR 생성 전에 해결해야 하는 문제를 작성하세요.

### 개선을 권장하는 문제

### 이상 없는 항목

### 테스트 결과

### PR 작성 시 주의사항

문제를 발견하더라도 자동으로 대규모 수정하지 말고 수정 대상과 방안을 먼저 제안하세요.
```

## 18. Merge 규칙

Pull Request가 승인되고 검증이 완료된 경우에만 Merge합니다.

Merge 전 다음 내용을 확인합니다.

* 리뷰어 승인 여부
* 코드 충돌 여부
* CI 검사 통과 여부
* 테스트 결과
* 기준 브랜치 최신 반영 여부
* 관련 문서 수정 여부

프로젝트에서 정한 Merge 방식을 사용합니다.

* Squash and Merge
* Rebase and Merge
* Merge Commit

팀에서 별도 기준이 없다면 하나의 작업을 하나의 Commit으로 정리하기 쉬운 `Squash and Merge`를 권장합니다.

Merge 완료 후 사용이 끝난 작업 브랜치는 삭제합니다.

## 19. 충돌 방지 규칙

작업 기간이 길어질 경우 기준 브랜치의 최신 변경사항을 주기적으로 확인합니다.

다음 파일은 충돌이 자주 발생하므로 변경 전 팀원과 공유하는 것을 권장합니다.

* 라우팅 파일
* 전역 스타일
* 디자인 토큰
* 공통 레이아웃
* 공통 컴포넌트
* 공통 타입
* API Client
* `package.json`
* lock 파일
* 환경 설정
* Barrel Export용 `index` 파일

공통 파일은 전체를 다시 작성하지 않고 필요한 부분만 최소한으로 수정합니다.

## 20. 보안 규칙

다음 정보는 GitHub에 Commit하지 않습니다.

* API Key
* Access Token
* 비밀번호
* 인증서
* 개인 정보
* 운영 서버 주소
* 데이터베이스 접속 정보
* 실제 사용자 데이터
* `.env` 파일

환경 변수 예시는 실제 값 없이 `.env.example`에 작성합니다.

```env
API_URL=
API_KEY=
```

AI에게 민감 정보가 포함된 파일을 그대로 전달하지 않습니다.

## 21. 금지 사항

다음 행동은 원칙적으로 금지합니다.

* `main`, `master`, `develop` 직접 수정
* 강제 Push
* 다른 작업자의 브랜치 삭제
* 기존 Git 이력 변경
* 리뷰 없이 Merge
* 테스트 실패 상태에서 Merge
* 환경 변수 및 비밀키 Commit
* 요청받지 않은 전체 리팩터링
* 요청받지 않은 패키지 설치
* 요청받지 않은 데이터베이스 변경
* 확인 없는 배포
* AI가 생성한 코드의 무검토 반영
* 동작 확인 없이 작업 완료 처리
* 실행하지 않은 검증을 실행했다고 보고

## 23. 최종 책임

AI는 개발을 보조하는 도구입니다.

AI가 생성한 코드라도 최종적으로 다음 항목은 작업자가 직접 확인해야 합니다.

* 코드의 정확성
* 기획 및 디자인 반영 여부
* 기존 기능 영향 여부
* 보안 문제
* 접근성
* 반응형
* 테스트 결과
* Git 변경 범위
* Pull Request 내용

AI의 답변이나 코드가 프로젝트 규칙과 충돌하는 경우 이 문서의 규칙을 우선합니다.
