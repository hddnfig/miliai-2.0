## 1. Executive Summary

MILI AI는 콘텐츠 유형별 카탈로그가 아니라 **현실 문제를 AI로 해결하는 학습 여정**을 중심으로 재구성한다. 학습자는 `탐색 → 지식 학습 → 프로젝트 → 미션 → 제출 → 피드백 → 개선 → 성장 축적`을 하나의 끊김 없는 흐름으로 경험한다. VOD는 독립 목적이 아니라 프로젝트 수행에 필요한 지식을 공급하며, AI 교관은 별도 게시판이 아니라 모든 학습 화면에서 현재 맥락을 이해하는 공통 도구로 둔다.

학습자 GNB는 사용 빈도와 과업을 기준으로 `홈 / 탐색 / 내 학습 / 함께 학습 / 나의 성장`의 5개로 권장한다. 검색·알림·AI 교관·프로필은 공통 유틸리티다. 모바일 하단 탐색은 `홈 / 탐색 / 내 학습 / 성장 / MY`로 단순화하고 AI 교관은 학습 문맥에서 호출한다.

지휘관은 교육 현황과 지원, 콘텐츠 설계자는 학습 설계와 검수, 운영자는 정책·권한·시스템 운영에 집중하도록 워크스페이스를 분리한다. 지휘관에게 개인 AI 대화 원문이나 과도한 세부 활동을 기본 제공하지 않는다.

## 3. 권장 플랫폼 구조

```text
MILI AI
├─ 학습 경험
│  ├─ 탐색·추천
│  ├─ VOD 지식 학습
│  ├─ 프로젝트·미션 수행
│  ├─ 제출·평가·개선
│  └─ 팀·동료학습
├─ 성장 경험
│  ├─ 역량 지도
│  ├─ 성장 기록
│  ├─ 성취·인증
│  └─ 포트폴리오
├─ 공통 지능
│  ├─ 맥락형 AI 교관
│  ├─ 추천
│  ├─ 검색
│  └─ 알림
└─ 운영 워크스페이스
   ├─ 지휘관
   ├─ 콘텐츠 설계자
   └─ 플랫폼 운영자
```

### 3.1 핵심 설계 원칙

1. 프로젝트를 중심축으로 두고 VOD·AI·평가를 수행 맥락에 연결한다.
2. 학습 신청, 진도, 제출, 평가 상태를 한 화면에서 해석할 수 있게 통합한다.
3. 세계관은 메뉴를 대체하지 않고 상태·성취·전환 순간에 사용한다.
4. 개인 성과와 조직 통계를 분리하고 최소 권한·목적 제한을 적용한다.
5. 모바일은 확인·짧은 학습·피드백, PC는 제작·코딩·대용량 제출을 우선한다.
6. 학습 완료보다 피드백 반영과 재제출을 핵심 성공 행동으로 본다.

| 사용자 유형 | 핵심 목적 | 주요 권한 | 제한 원칙 | 데이터 범위 |

| 학습자 | 학습하고 문제 해결 결과를 축적 | 학습 참여, 제출, 평가, 포트폴리오 관리 | 타인의 비공개 결과·개인정보 접근 금지 | 본인 및 허용된 팀 데이터 |
| 팀 리더 | 팀 수행 조율 | 역할·일정 조율, 공동 제출 확인 | 교육평가자 권한과 분리 | 소속 팀 프로젝트 |
| 지휘관·교육담당 | 교육 참여·성과 확인 및 지원 | 집계 조회, 대상 배정, 리포트 | AI 대화 원문·민감 결과 기본 비공개 | 허용된 부대 계층 |
| 콘텐츠 설계자 | 과정·프로젝트·평가 설계 | 초안 작성, 버전 관리, 검수 요청 | 게시·정책 변경은 승인 분리 | 담당 콘텐츠 |
| 평가자·멘토 | 제출물 평가·피드백 | 루브릭 평가, 수정 요청 | 배정된 제출물만 접근 | 배정 범위 |
| 플랫폼 운영자 | 서비스·회원·정책 운영 | 계정·권한·공지·통계·감사 | 콘텐츠 전문 검수와 시스템 권한 분리 | 운영 목적 범위 |
| 시스템 관리자 | 안정성·보안 관리 | 설정, 연동, 감사로그 | 학습 내용 열람 최소화 | 기술 메타데이터 중심 |

### 4.1 권한 모델 권고

- RBAC로 역할의 기본 권한을 부여하고, 조직·프로젝트·콘텐츠 범위는 ABAC 조건으로 제한한다.
- `role`, `permission`, `role_permission`, `user_role`, `scope_assignment`를 분리한다.
- 지휘관 범위는 단순 `unit_id`가 아니라 유효기간과 허용 조직 트리를 가진다.
- 콘텐츠 작성·검수·게시와 평가 배정·수행은 상호 분리 가능한 권한으로 둔다.
- AI 대화, 결과물, 개인 진단은 별도 민감도 등급과 감사 기록을 적용한다.

### 5.2 모바일 정보 구조

- 하단: `홈 / 탐색 / 내 학습 / 성장 / MY`
- `함께 학습`은 홈의 할 일과 프로젝트 대시보드에서 우선 진입하고 전체 메뉴에도 둔다.
- AI 교관은 항상 떠 있는 장식형 버튼보다 학습 문맥 내 `AI 교관에게 묻기`를 우선한다.
- 파일·Git·코드 결과 제출은 모바일에서 상태 확인과 초안 작성까지만 지원하고 `PC에서 이어하기`를 제공한다.

| 권한 | 역할·권한 | L1 | 최소 권한 운영 | 역할·범위 부여, 감사 | 역할, 권한, 접근 범위 | `tb_role`, `tb_member_role`, `tb_menu_role`; 데이터 범위는 추가 설계 | 민감 데이터 접근 통제 |
| 교육 운영 | 교육 운영 | L1 | 모집·신청·평가 운영 | 승인, 일정, 평가 배정 | 모집, 신청, 평가, 인증 | PBL/VOD offering·enrollment, `tb_cert_issue`; 평가 배정은 추가 설계 | 운영자의 일괄 처리 과업 중심 |
| 소통 | 공지·알림 | L1 | 대상별 메시지 관리 | 작성, 예약, 발송 확인 | 공지, 템플릿, 발송 이력 | `tb_board`, `tb_post`, `tb_message_template`, `tb_message_history` | 인앱과 외부 채널 일관성 확보 |

## 9. 핵심 사용자 플로우

### 9.1 신규 학습자

```text
로그인 → 약관·보안 안내 → 관심 분야·목표 → 초기 진단(선택/필수 정책)
→ 추천 경로 확인 → 첫 학습 저장 → 홈에서 다음 행동 확인
```

### 9.2 프로젝트 기반 학습

```text
탐색/추천 → 프로젝트 상세 → 선수학습 확인 → 참여 신청/즉시 시작
→ 프로젝트 대시보드 → 미션 수행 ↔ AI 교관
→ 결과물 초안·검증 → 제출 → AI/동료/멘토 평가
→ 수정 필요 시 피드백 반영 → 재제출 → 프로젝트 완료
→ 역량 근거·포트폴리오 축적
```

분기:

- 잠금: 충족하지 않은 조건과 바로 갈 수 있는 선수학습을 제시한다.
- 팀 프로젝트: 참여 직후 팀 공간·역할·일정 합의로 이동한다.
- 평가 지연: 상태와 예상 처리 기준을 표시하고 중복 제출을 막는다.
- 실패: 결과를 낙인화하지 않고 `보완 필요`와 재시도 조건을 제시한다.

### 9.3 VOD 지식 학습

```text
과정 상세 → 수강 시작 → 차시 학습 → 지식 확인 → 진도 저장
→ 다음 차시 또는 연결 프로젝트 추천 → 수료 조건 충족 → 인증·역량 근거 반영
```

### 9.4 동료평가

```text
평가 요청 알림 → 이해충돌·익명 정책 확인 → 제출물 열람
→ 루브릭 항목 평가 → 근거 있는 피드백 작성 → 제출
→ 평가 품질 확인 → 참여 기록 반영
```

### 9.5 지휘관 교육 지원

```text
교육 현황 → 부대/기간 필터 → 지원 필요 신호 확인
→ 학습자 또는 그룹 수준 원인 확인 → 지원 안내/계획 조정
→ 조치 기록 → 이후 변화 확인 → 보고서 생성
```

## 10. 상태값 정의

상태는 한 필드에 모두 넣지 않고 생애주기별로 분리한다.

| 상태군 | 권장 값 | 사용자 표시 | 원칙 |
|---|---|---|---|
| 참여 신청 | `APPLIED`, `ACCEPTED`, `DENIED`, `CANCELED` | 승인 대기, 승인, 반려, 취소 | 반려 사유와 재신청 정책 필요 |
| 학습 실행 | `NOT_STARTED`, `READY`, `IN_PROGRESS`, `COMPLETED`, `EXPIRED` | 시작 전, 시작 가능, 학습 중, 완료, 기간 종료 | 신청 상태와 분리 |
| 미션 실행 | `LOCKED`, `READY`, `IN_PROGRESS`, `SUBMITTED`, `COMPLETED` | 잠김, 시작 가능, 수행 중, 제출됨, 완료 | 완료는 평가 조건 충족 후 |
| 결과물 | `DRAFT`, `SUBMITTED`, `WITHDRAWN`, `RESUBMITTED` | 작성 중, 제출 완료, 철회, 재제출 | 버전은 별도 엔티티로 보존 |
| 평가 작업 | `REQUESTED`, `ASSIGNED`, `IN_REVIEW`, `COMPLETED`, `EXPIRED` | 요청, 배정, 평가 중, 평가 완료, 기한 종료 | 평가자 작업 상태 |
| 평가 결과 | `PASS`, `REVISION_REQUIRED`, `FAIL` | 통과, 수정 필요, 미통과 | 상태가 아닌 판정으로 분리 |
| 콘텐츠 | `DRAFT`, `IN_REVIEW`, `APPROVED`, `PUBLISHED`, `ARCHIVED` | 초안, 검수 중, 승인, 게시, 보관 | 게시 버전 불변 권고 |
| 알림 | `UNREAD`, `READ`, `ARCHIVED` | 읽지 않음, 읽음, 보관 | 발송 성공과 읽음 상태 분리 |
| 인증 | `ISSUED`, `REVOKED`, `EXPIRED` | 발급, 취소, 만료 | 취소 사유·검증키 보존 |

ERD 메모에서 확인한 `PREPARING/READY/LEARNING/FINISHED`, `STANDBY/DOING/DONE/EVALUATED`는 위 권장 상태와 의미를 매핑하되, DDL·실데이터 확인 전 임의 변경하지 않는다.

## 13. 최종 권고안

1. 첫 릴리스는 `프로젝트 1개를 찾아 미션을 수행하고 피드백을 반영해 완료하는 흐름`을 수직으로 완성한다.
2. 원본 DB 스키마 없이는 구현 범위를 확정하지 않는다. UI 설계 전에 테이블·컬럼·PK/FK·enum·인덱스·보존정책을 포함한 데이터 사전을 확보한다.
3. 세계관은 `경험 레이어`로 구현한다. 기능명은 명확하게 두고, 진행·연결·완료 순간에 빛·선·결정·흔적의 표현을 사용한다.
4. 학습 완료 수가 아니라 결과물 개선과 역량 근거 축적을 핵심 성과 지표로 둔다.
5. 지휘관 화면은 순위 경쟁보다 참여 격차와 지원 필요 신호를 보여주며 개인 민감정보 노출을 최소화한다.
