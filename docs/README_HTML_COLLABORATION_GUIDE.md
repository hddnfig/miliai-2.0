# 기획·디자인 HTML 협업 가이드

## 1. 문서 목적

이 저장소는 **기획자와 디자이너가 함께 화면 정책과 UI를 정의하고, AI 도구를 활용해 외부 개발사 전달용 HTML 산출물을 제작하기 위한 공간**입니다.

실제 서비스 개발은 외부 개발사에서 별도로 진행합니다. 이 저장소의 HTML, CSS, JavaScript는 운영 코드가 아니라 다음 내용을 전달하는 기준 자료입니다.

- 화면 구조와 정보 위계
- 사용자 흐름
- 화면별 기획 정책
- UI 디자인
- 공통 컴포넌트
- 컴포넌트 상태
- 반응형 동작
- 주요 인터랙션
- 로딩·빈 상태·오류·권한 등 예외 상황

외부 개발사는 최종 승인된 HTML 산출물을 참고하여 실제 개발 환경과 기술 구조에 맞게 서비스를 구현합니다.

---

## 2. 협업 범위와 역할

### 기획자가 결정하는 내용

- 기능 목적
- 사용자 흐름
- 정보 구조
- 진입 및 노출 조건
- 버튼 활성화 조건
- 입력 및 검증 조건
- 데이터 정렬과 노출 기준
- 권한 정책
- 화면 이동
- 로딩·빈 상태·오류·예외 정책

### 디자이너가 결정하는 내용

- 화면 레이아웃
- 정보의 시각적 우선순위
- 공통 컴포넌트 표현
- 디자인 토큰 적용
- 반응형 UI
- 인터랙션 표현
- 모션
- 접근성 표현

### 공동으로 결정하는 내용

- 화면 구성
- 핵심 사용자 행동
- 콘텐츠 우선순위
- 컴포넌트 상태
- 빈 상태와 오류 상태
- 모바일 화면 구조
- 주요 인터랙션
- 외부 개발사에 전달할 HTML 범위

AI는 기획자와 디자이너의 결정을 보조할 수 있지만, **확정되지 않은 정책이나 디자인을 임의로 결정하지 않습니다.**

## 3. 전체 작업 흐름

```text
기획 정의
→ 화면 구조 및 정책 정리
→ 디자인 적용
→ HTML 프로토타입 제작
→ 기획·디자인 내부 검토
→ 수정 및 승인
→ main 반영
→ 버전 태그 생성
→ 외부 개발사 전달
```

기획, 디자인, HTML 작업은 병행할 수 있습니다. 다만 승인되지 않은 내용은 최종 전달본에 포함하지 않습니다.

## 4. 브랜치 운영 원칙

### `main`

외부 개발사에 전달할 수 있는 **최종 승인본**만 관리합니다.

다음 조건을 모두 확인한 작업만 `main`에 반영합니다.

- 기획 검토 완료
- 디자인 검토 완료
- 화면별 정책 확인 완료
- 주요 상태 확인 완료
- 반응형 확인 완료
- 주요 인터랙션 확인 완료
- 미확정 항목 표시 완료
- 전달 대상 파일 확인 완료
- 내부 Pull Request 리뷰 완료

`main`에서 직접 작업하거나 커밋하지 않습니다.

### `develop`

기획과 디자인 작업을 통합하고 검토하는 **내부 통합 브랜치**입니다.

각 작업 브랜치는 `develop`을 기준으로 생성하며, 작업 완료 후 Pull Request를 통해 `develop`에 반영합니다.

```bash
git checkout develop
git pull origin develop
git checkout -b design/home-dashboard
```

### 작업 브랜치

한 브랜치에는 하나의 명확한 작업 목적만 포함합니다.

가능하면 서로 다른 화면이나 기능을 하나의 브랜치에서 동시에 수정하지 않습니다.

## 5. 브랜치 이름 규칙

브랜치명은 아래 형식을 사용합니다.

```text
작업유형/작업내용
```

| 작업 유형 | Prefix | 예시 |
|---|---|---|
| 기획 및 정책 | `planning/` | `planning/learning-policy` |
| 화면 구조 | `structure/` | `structure/course-detail` |
| UI 디자인 | `design/` | `design/home-dashboard` |
| HTML 프로토타입 | `prototype/` | `prototype/onboarding-flow` |
| UI 수정 | `ui/` | `ui/navigation-layout` |
| 오류 수정 | `fix/` | `fix/mobile-card-overflow` |
| 공통 요소 | `component/` | `component/button-states` |
| 문서 | `docs/` | `docs/update-handoff-guide` |
| 설정 및 정리 | `chore/` | `chore/organize-assets` |

브랜치명은 영문 소문자와 하이픈을 사용합니다.

```text
planning/user-growth-policy
design/learning-dashboard
prototype/ai-coaching-flow
fix/mobile-navigation
```

1. 현재 브랜치
2. Git 변경 상태
3. `develop` 최신 반영 여부
4. 작업 요청 및 관련 Issue
5. 관련 기획 문서
6. 관련 Figma
7. 기존 프로젝트 구조
8. 유사 화면 및 컴포넌트

10. 변경 예정 파일과 영향 범위

12. 미확정 정책 또는 디자인

AI에게 작업을 요청할 때도 바로 수정하게 하지 않고, 먼저 다음 내용을 보고하도록 합니다.

- 작업 요청 이해 내용
- 구현 계획
- 변경 예정 파일
- 재사용할 기존 요소
- 기획상 확인이 필요한 내용
- 디자인상 확인이 필요한 내용
- 다른 화면에 미치는 영향
- 예상 충돌 가능성

## 7. 작업 범위 원칙

요청받은 범위 안에서만 파일을 수정합니다.

다음 항목은 별도 협의 없이 변경하지 않습니다.

- 관련 없는 화면
- 다른 작업자의 담당 화면
- 공통 컴포넌트 구조
- 공통 디자인 토큰
- 전역 스타일
- 전체 폴더 구조
- 공통 JavaScript 구조
- 외부 라이브러리
- 패키지 및 프로젝트 설정
- 기존 파일명과 경로
- 다수 파일의 일괄 포맷팅
- 승인된 기존 기능과 인터랙션

작업 범위를 넘어서는 변경이 필요하다면 다음 내용을 먼저 공유합니다.

- 추가 변경이 필요한 이유
- 변경 대상 파일
- 예상 영향 범위
- 변경하지 않았을 때 발생하는 문제
- 가능한 대안

승인되지 않은 변경은 진행하지 않습니다.

## 8. 권장 저장소 구조

아래 구조를 기본으로 사용하되, 이미 저장소 구조가 존재한다면 무조건 재구성하지 않고 현재 구조와의 호환성을 먼저 검토합니다.

```text
/
├── README.md
├── index.html
│
├── pages/
│   ├── home.html
│   ├── onboarding.html
│   ├── course-list.html
│   └── course-detail.html
│
├── components/
│   ├── button.html
│   ├── card.html
│   ├── modal.html
│   └── navigation.html
│
├── styles/
│   ├── tokens.css
│   ├── common.css
│   ├── components.css
│   └── pages.css
│
├── scripts/
│   ├── common.js
│   └── interactions.js
│
├── assets/
│   ├── images/
│   ├── icons/
│   └── fonts/
│
└── archive/
    └── 이전 버전 또는 폐기된 화면
```

### `index.html`

외부 개발사와 내부 검토자가 모든 화면을 한곳에서 확인하는 **화면 인덱스 및 전달 허브**입니다.

화면별로 다음 정보를 표시하는 것을 권장합니다.

- 화면명
- 화면 ID
- 파일 경로
- 작업 상태
- 최종 수정일
- Desktop·Tablet·Mobile 지원 여부
- 주요 인터랙션
- 미확정 항목
- 관련 화면 링크

### `pages`

실제 서비스 화면 단위의 HTML을 관리합니다.

### `components`

버튼, 카드, 모달, 탭, 내비게이션 등 공통 UI의 예시와 상태를 관리합니다.

### `styles`

디자인 토큰과 공통 스타일을 관리합니다. 페이지마다 같은 값을 반복해서 작성하지 않습니다.

### `scripts`

화면 흐름과 인터랙션 확인에 필요한 최소한의 JavaScript만 작성합니다.

실제 API 통신, 데이터베이스 처리, 인증, 운영 로직은 구현하지 않습니다.

### `archive`

폐기되었거나 이전 버전으로 보존해야 하는 화면을 관리합니다.

현재 전달 대상과 혼동되지 않도록 파일명이나 문서에 상태를 명시합니다.

## 9. HTML 전달 산출물 기준

### 실행 기준

- 가능하면 별도의 빌드 없이 실행할 수 있어야 합니다.
- `index.html`에서 전체 전달 화면에 접근할 수 있어야 합니다.
- 로컬에서 파일을 열어도 경로가 깨지지 않아야 합니다.
- 이미지, 아이콘, 스타일, 스크립트는 저장소 내부 상대 경로를 사용합니다.
- 승인되지 않은 외부 CDN에 의존하지 않습니다.
- 별도의 실행 환경이나 빌드가 필요하면 README에 방법을 명시합니다.
- 외부 개발사에 불필요한 임시 파일은 전달본에서 제외합니다.

### 화면 기준

각 화면에는 필요한 범위에서 다음 내용이 포함되어야 합니다.

- 실제 화면에 가까운 레이아웃
- 현실적인 샘플 콘텐츠
- 주요 컴포넌트 상태
- 화면 이동 흐름
- 주요 인터랙션
- Desktop·Tablet·Mobile 대응
- 긴 텍스트
- 데이터 최소·최대 상황
- 로딩 상태
- 빈 상태
- 오류 상태
- 권한 제한 상태
- 이미지가 없는 상태

모든 화면에 모든 상태를 억지로 포함하지 않고, 실제 정책상 필요한 상태만 제공합니다.

## 10. HTML 파일 상단 주석 규칙

각 화면 HTML 파일 상단에 아래 형식의 주석을 작성합니다.

```html
<!--
화면명: 강의 상세
화면 ID: COURSE-DETAIL-001
버전: 1.2.0
상태: 최종 승인
담당: 기획 / 디자인
최종 수정일: YYYY-MM-DD

지원 화면:
- Desktop: 1440px 기준
- Tablet: 768px 이상
- Mobile: 360px 이상

주요 인터랙션:
- 수강하기 선택 시 학습 화면으로 이동
- 챕터 선택 시 해당 챕터 상세 노출
- 완료된 챕터는 완료 상태로 표시

포함 상태:
- 기본
- 수강 전
- 수강 중
- 수강 완료
- 로딩
- 오류
- 빈 상태

미확정 사항:
- 없음

참고:
- 본 HTML은 화면, 정책 및 인터랙션 전달용입니다.
- 실제 API, 인증, 데이터베이스 및 운영 로직은 포함하지 않습니다.
-->
```

미확정 내용이 있다면 `없음`으로 작성하지 않고 구체적으로 표시합니다.

## 11. 미확정 사항 표기

기획, 디자인, 콘텐츠가 확정되지 않은 경우 AI나 작업자가 임의로 결정하지 않습니다.

HTML 주석에는 다음 형식을 사용합니다.

```html
<!-- POLICY-TBD:
사용자가 학습을 중단한 경우 이어보기 위치를
마지막 완료 챕터로 할지 마지막 접근 챕터로 할지 확인 필요
-->
```

```html
<!-- DESIGN-TBD:
모바일 환경에서 해당 모달을 바텀시트로 전환할지 확인 필요
-->
```

```html
<!-- CONTENT-TBD:
빈 상태 안내 문구 최종 확정 필요
-->
```

정책이 확정되면 주석, 화면 UI, 관련 인덱스 정보를 함께 수정합니다.

- 화면 목적
- 사용자 진입 조건
- 사용자 행동
- 화면 이동
- 노출 조건
- 버튼 활성화 조건
- 입력 조건
- 검증 조건
- 권한 조건
- 데이터 정렬 기준
- 데이터 노출 우선순위
- 최대·최소 노출 수
- 로딩 상태
- 빈 상태

## 13. 디자인 적용 기준

디자인 적용 우선순위는 다음과 같습니다.

```text
공통 디자인 시스템
→ 디자인 토큰
→ 공통 컴포넌트
→ 화면별 Figma
→ 기존 유사 화면
```

UI 작업 시 다음 내용을 확인합니다.

- 컬러
- 타이포그래피
- 간격
- 그리드
- 이미지 비율
- 아이콘
- 정보 위계
- 컴포넌트 상태
- 반응형 변화
- 콘텐츠 길이 변화
- 키보드 접근성
- 포커스 표현
- 모션과 인터랙션

동일한 역할의 UI를 화면마다 다른 방식으로 만들지 않습니다.

## 14. 컴포넌트 상태 기준

필요한 컴포넌트에는 다음 상태를 정의합니다.

### 사용자 인터랙션 상태

- Default
- Hover
- Focus
- Active
- Selected
- Disabled

### 비동기 상태

- Loading
- Success
- Error

### 데이터 상태

- Empty
- Partial
- Maximum
- Overflow

### 사용자 및 권한 상태

- 비로그인
- 접근 가능
- 접근 제한
- 관리자 전용

상태가 실제 화면 정책과 연결되는지 기획자와 디자이너가 함께 검토합니다.

## 15. 반응형 기준

화면별로 Desktop, Tablet, Mobile에서 달라지는 요소를 명시합니다.

```html
<!--
반응형 정책:

Desktop
- 콘텐츠 카드 4열
- 좌측 사이드바 고정
```

## 16. AI 활용 원칙

Cursor, Codex, Claude Code 등 어떤 AI를 사용하더라도 동일한 규칙을 적용합니다.

AI가 생성한 HTML, CSS, JavaScript는 반드시 사람이 검토합니다.

### AI가 임의로 결정하면 안 되는 내용

- 새로운 기능
- 화면 정책
- 사용자 권한
- 데이터 노출 기준
- 버튼 활성화 조건

- 새로운 디자인 스타일
- 디자인 토큰 값
- 반응형 정책
- 공통 컴포넌트 구조
- 외부 개발사 전달 범위

명시되지 않은 내용은 기존 문서와 구현을 확인합니다. 그래도 판단할 수 없다면 `TBD`로 남깁니다.

- 프레임워크 도입
- 외부 CDN 추가
- 전체 코드 포맷팅
- 전체 폴더 구조 변경

- 배포

## 21. 내부 리뷰 기준

### 기획 리뷰

- 사용자 흐름이 맞는가
- 진입 및 노출 조건이 맞는가
- 입력과 검증 조건이 맞는가
- 데이터 정책이 반영되었는가
- 버튼 동작이 명확한가
- 빈 상태와 오류 상태가 정의되었는가
- 화면 이동이 연결되어 있는가
- 임의로 추가된 정책이 없는가

### 디자인 리뷰

- 디자인 시스템이 적용되었는가
- 공통 컴포넌트를 재사용했는가
- 정보 우선순위가 적절한가
- 주요 상태가 표현되었는가
- 모바일 화면이 자연스러운가
- 긴 텍스트에서도 문제가 없는가
- 인터랙션을 확인할 수 있는가
- 접근성이 고려되었는가

### 전달본 리뷰

- `index.html`에서 모든 화면을 확인할 수 있는가
- 파일 경로가 깨지지 않는가
- 이미지와 아이콘이 누락되지 않았는가
- 미확정 사항이 명확한가
- 폐기된 화면이 섞여 있지 않은가
- 임시 데이터와 실제 정책이 구분되는가
- 최종 버전이 명확하게 표시되어 있는가

## 22. 외부 개발사 전달 규칙

외부 개발사에는 `main` 브랜치 또는 지정된 버전 태그의 파일만 전달합니다.

`develop`과 개별 작업 브랜치는 내부 작업용이며 전달 기준으로 사용하지 않습니다.

### 태그 예시

```text
handoff-v1.0.0
handoff-v1.1.0
handoff-v1.1.1
```

### 버전 기준

- 첫 번째 숫자: 전체 구조 또는 주요 정책 변경
- 두 번째 숫자: 화면 또는 기능 추가
- 세 번째 숫자: UI, 문구 및 오류 수정

외부 개발사에서 받은 질문이나 수정 요청은 Issue로 등록하는 것을 권장합니다.

외부 요청을 확인 없이 HTML에 직접 반영하지 않고, 기획과 디자인 검토 후 별도 브랜치에서 수정합니다.

## 23. HTML 산출물의 책임 범위

HTML 산출물은 다음 항목의 기준입니다.

- 화면 구조
- 정보 위계
- 콘텐츠 우선순위
- UI 형태
- 주요 상태
- 반응형 변화
- 사용자 인터랙션
- 화면 이동
- 기획 정책의 화면 표현

HTML 산출물은 다음 구현을 보장하지 않습니다.

- 실제 API 통신
- 데이터베이스
- 서버 처리
- 인증 및 보안
- 실제 권한 로직
- 성능 최적화
- 운영 환경 설정
- 외부 개발사의 코드 구조
- 실제 서비스 프레임워크 구조

외부 개발사는 HTML을 그대로 운영 코드로 복사하기보다 실제 개발 환경과 기술 구조에 맞게 구현해야 합니다.

단, 최종 화면 결과와 사용자 경험은 전달된 HTML 및 확정 정책과 일치해야 합니다.

## 24. 금지 사항

- `main` 또는 `develop`에서 직접 작업
- 검토되지 않은 파일을 `main`에 반영
- AI가 기획 정책을 임의로 결정
- AI가 디자인 스타일을 임의로 추가
- 다른 작업자의 화면을 확인 없이 수정
- 전체 파일 일괄 포맷팅
- 요청하지 않은 공통 구조 변경
- 불필요한 패키지 또는 프레임워크 도입
- 승인되지 않은 외부 CDN 사용
- 미확정 내용을 확정된 내용처럼 전달
- 폐기된 화면을 최종 전달본에 포함
- 버전 표시 없이 외부 개발사에 전달
- AI 생성 결과를 검토 없이 반영
- 실행하지 않은 검증을 완료했다고 보고
